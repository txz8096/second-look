Might help

Try this: brief before big prototype tasks

Before a prototype session you expect to run past 15 minutes, write the goal, the user, what done means and the constraints. A /brief skill can prompt you. Skip it for quick fixes. If you're exploring and don't know done yet, just say "exploring."

Brief template
Goal: [what this prototype should let someone do]
User: [who uses it]
Done when: [what you'll check to call it finished]
Constraints: [stack, scope, what not to touch]
Before building, list up to 3 questions you need answered.

Finished-looking prototypes get waved through

Claude Code · claude.aiUnconfirmed
What happens
When a prototype looks done, you tend to accept it without asking for edge cases, a critique or a test. You push back on text answers far more.
Evidence
3 prototypes went into the Streak beta with "perfect, ship it" as the last message. Checking in prototype sessions fell from 46% to 18% once the redesign started. You challenge text-only answers 2.4× as often.
Why it matters
Beta testers use what you ship. A broken interaction there costs more than one in a sketch.
Worth testing

Try this: check beta work before it ships

Only for work others will see: run your review checklist, or ask "What are the 3 most likely ways this breaks for a real user, and what did you assume that I didn't tell you?" Skip it for internal or throwaway work.
